# ADR 0009: клиентский read model заказов

Статус: принято. Дата: 2026-10-13.

## Контекст

ADR 0008 выдаёт tenant-scoped customer session после OTP, но до этого изменения
сессия могла прочитать только собственную identity. Этап онлайн-заказа требует
список и карточку заказа в будущем личном кабинете. Публичный staging пока не
имеет реального SMS-провайдера, поэтому этот этап реализует серверную read-only
границу, не открывая неработающий UI.

## Решение

- `GET /api/v1/r/{tenant_slug}/me/orders` возвращает страницу заказов клиента.
  `limit` ограничен 1–50, `offset` — 0–10000; порядок стабилен по времени создания
  и UUID. Ответ содержит `total`, фактические параметры страницы и элементы.
- `GET /api/v1/r/{tenant_slug}/me/orders/{order_id}` возвращает один заказ или
  одинаковый 404 для отсутствующего и чужого заказа.
- Bearer token хэшируется до обращения к хранилищу. Customer session проверяется
  внутри той же tenant/RLS-транзакции, что и запрос заказов; истёкшая session
  переводится в `expired` и отвечает 401 с `WWW-Authenticate: Bearer`.
- Каждый запрос одновременно материализует истёкшие hold/order состояния. Поэтому
  клиентская история продолжает показывать `expired` и `cancelled`, тогда как
  анонимный checkout endpoint по-прежнему показывает только активный draft.
- Read model возвращает снимок цены, даты, способ получения и публичное состояние.
  Он не возвращает телефон, `customer_id`, `checkout_session_id`, asset/serial,
  idempotency hashes или внутренние события. Оплата остаётся `not_started`, а
  `confirmation_available=false`.
- Чтение ограничено Redis rate limit по хэшу customer session. Запрос с токеном
  другого клиента или tenant не пересекает границу данных.

## Граница этапа

Read model не подтверждает заказ, не продлевает hold и не добавляет customer UI.
На staging SMS и booking остаются выключенными, поэтому получить customer session
через публичную витрину нельзя. Имена модели и филиала пока не входят в неизменяемый
quote snapshot; перед полноценным кабинетом snapshot нужно расширить, чтобы история
не зависела от последующего переименования каталога.

## Проверки

Интеграционный сценарий проверяет список и карточку, пагинацию, отсутствие
внутренних полей, изоляцию двух клиентов одного tenant, изоляцию tenant, ротацию и
истечение session, а также чтение заказа после перехода `held → expired`. OpenAPI
тест фиксирует `identity_verified=true`, `payment_status=not_started` и запрет
подтверждения.
