# ADR 0003: tenant-каталог, инвентарь и публичная read-model

Статус: принято. Дата: 2026-10-13.

## Контекст

Витрина должна показывать каталог конкретного арендодателя из PostgreSQL, но
публичный запрос не должен раскрывать серийные номера, внутренние коды и служебные
статусы отдельных приборов. Проверка доступности на даты и оформление заказа ещё
не реализованы, поэтому текущие количества нельзя выдавать за подтверждённую бронь.

## Решение

- `storefront_profiles` хранит явно опубликованный профиль, город, тему и признаки
  demo/booking. Один только существующий tenant не становится публичным.
- `branches`, `equipment_models`, `assets` и `pricing_rules` всегда содержат
  `tenant_id`. Ссылки asset → branch/model и pricing → model используют составные
  FK `(tenant_id, id)`, поэтому невозможно связать строки разных организаций.
- На всех пяти таблицах включены `ENABLE/FORCE ROW LEVEL SECURITY` с тем же
  transaction-local `app.tenant_id`, что и в ADR 0002. Без scope таблицы пусты для
  runtime-роли; scope сбрасывается вместе с транзакцией.
- Узкая `SECURITY DEFINER` функция разрешает slug только для явно опубликованной
  витрины и возвращает tenant ID. После этого API устанавливает RLS scope и строит
  публичную read-model обычными запросами под `photolamp_runtime`.
- `GET /api/v1/r/{tenant_slug}/catalog` публикует карточки моделей, филиалы,
  активный тариф и агрегированные количества. Asset IDs, `asset_code`, `serial_no`,
  даты проверок и служебные состояния в DTO отсутствуют.
- Денежные значения хранятся в копейках. Текущие seed-тарифы полностью
  синтетические, имеют `is_demo=true` и в UI подписаны как демо. Ответ содержит
  `availability_confirmed=false`, а booking остаётся выключенным.

## Демонстрационные данные

Миграция создаёт два детерминированных demo tenant только для локальной/staging
витрины. Они не содержат телефонов, адресов, клиентов, заказов, реальных серийных
номеров или иных персональных данных. В production demo-каталоги отвергаются
настройкой приложения даже при наличии строк в базе.

## Проверки и следующий шаг

Интеграционные тесты выполняются на настоящем PostgreSQL под runtime-ролью и
проверяют отсутствие данных без scope, изоляцию SELECT/UPDATE, сброс scope в пуле,
составной FK и отсутствие приватных asset-полей в публичном ответе. Управляемый
staff CRUD реализован в ADR 0004. Следующий этап добавит серверный
availability/quote. До атомарных allocation/hold и расчёта сервером кнопки
оформления остаются отключёнными.
