# IMPLEMENTATION_PLAN

## Общий принцип

Реализовывать проект поэтапно, небольшими PR, сохраняя рабочее состояние репозитория.

---

## Этап 0. Repo foundation

### Цель
Подготовить базовую структуру монорепозитория или согласованной структуры frontend/backend.

### Что сделать
- создать frontend app;
- создать backend app;
- добавить docs;
- добавить `.editorconfig`, `.gitignore`, базовые linters/formatters;
- настроить docker-compose для локального запуска;
- добавить README с инструкцией запуска.

### Критерии приёмки
- проект поднимается локально;
- есть базовые health endpoints;
- есть CI для lint/test/build.

## Этап 5. Заказ по телефону

### Цель
Реализовать административное оформление заказа оператором.

### Что сделать
- UI “Новый заказ по телефону”;
- поиск клиента по номеру телефона внутри tenant;
- оформление заказа оператором;
- отправка SMS со ссылкой на вход/заказ.

### Критерии приёмки
- оператор может оформить заказ целиком без участия клиента в интерфейсе;
- клиент потом может увидеть этот заказ в личном кабинете.

### Текущее состояние

Этап реализован без реального SMS: оператор создаёт подтверждённый заказ через
tenant-scoped UI, сервер повторно считает цену, атомарно резервирует физический
прибор и пишет actor audit. Телефон ищется по tenant-scoped HMAC, контактный
профиль и адрес заказа хранятся как AES-GCM ciphertext под FORCE RLS. После
будущего OTP тот же клиент видит телефонный заказ в личной истории. Demo принимает
только фиксированный синтетический контакт. Реальный SMS-провайдер, production
staff-auth и ротация ключей остаются следующими production-задачами. Расшифровка
контакта доступна только отдельной tenant-scoped и аудируемой командой во время
исполнения заказа.

## Этап 6. Исполнение заказа

### Цель
Поддержать доставку, передачу, возврат и проверки.

### Что сделать
- курьерские задачи;
- handover / pickup states;
- inspections;
- buffers / asset blocks;
- order events.

### Критерии приёмки
- можно пройти полный цикл аренды;
- прибор не возвращается в availability до завершения inspection.

### Текущее состояние

Реализовано ядро цикла: `confirmed → in_progress → returned → completed`, отдельная
аудируемая выдача расшифрованного контакта, атомарные состояния физического прибора
`available → rented → inspection → available|maintenance`, идемпотентные команды
и события. Назначение прибора остаётся активным до завершения осмотра. Курьерские
назначения, маршруты, просрочки и автоматические buffers остаются следующими шагами.

## Этап 7. Продления, уведомления, напоминания

### Цель
Автоматизировать post-order lifecycle.

### Что сделать
- extension requests;
- notification jobs;
- уведомления за 24 часа до окончания аренды;
- запрос возврата;
- просрочки.

### Критерии приёмки
- пользователь может запросить продление;
- система корректно решает конфликты по availability.

### Текущее состояние

Реализованы tenant-scoped запросы клиента на продление и возврат, решения
owner/admin/operator с идемпотентностью и аудитом, атомарное изменение effective
end date после повторной проверки allocation и asset blocks, а также вычисляемая
просрочка в таймзоне филиала. Исходный order snapshot не меняется. Handover и
решения создают дедуплицированные notification jobs без plaintext destination;
пока SMS-провайдер отключён, они честно остаются `blocked/provider_disabled` и не
считаются отправленными. Активный worker, реальная доставка SMS, оплата доплаты и
клиентский UI остаются отдельным production-этапом.

## Этап 8. Панель владельца арендатора

### Цель
Сделать usable админку.

### Что сделать
- dashboard;
- orders list;
- customers;
- assets;
- pricing;
- staff;
- settings.

### Критерии приёмки
- админ может управлять повседневной работой без прямой работы с БД.

### Текущее состояние

Добавлена tenant-scoped операционная сводка: подтверждения, выдачи, возвраты
сегодня и завтра, просрочки, осмотры, клиентские запросы и состояние парка. Сроки
считаются в IANA-таймзоне соответствующего филиала, списки не содержат контактов
клиента и идентификаторов физических приборов. Карточки показателей открывают
существующую очередь с серверным фильтром, а действия по заказу обновляют сводку.
Управление клиентами, настройками tenant и курьерскими назначениями остаётся
продолжением этапа.

Добавлен privacy-safe справочник команды: owner/admin видят memberships без
контактных данных, а active owner может менять подпись, роль и состояние доступа.
Собственную роль нельзя изменить из текущей сессии, последний active owner
защищён конкурентной блокировкой, изменения пишутся в audit events. Demo содержит
только синтетических сотрудников.

Добавлен рабочий staff-auth без внешней доставки: active owner создаёт истекающую
одноразовую ссылку, PostgreSQL хранит только hash токена, а сотрудник при
активации выбирает неперсональный login и пароль с salted scrypt hash. Активация
атомарно переводит membership из `invited` в `active` и выдаёт opaque HttpOnly
session; replay, expiry и revoke проверяются сервером и аудируются. Повторный
вход защищён Redis rate limit и 15-минутной блокировкой после пяти ошибок. SMS
пока не отправляется: ссылку владелец передаёт вручную. Password recovery,
MFA/passkeys, список сессий и принудительный global logout остаются production
hardening этапом.
