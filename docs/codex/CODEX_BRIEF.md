# CODEX_BRIEF

## Роль Codex

Ты работаешь над проектом **Photolamp-SaaS**. Это multi-tenant SaaS-платформа для аренды фотоламп и другого оборудования.

## Бизнес-контекст

- Первый пилот — собственный прокат в Уфе.
- Парк на старте: до 10 ламп.
- Основной канал заказов: сайт.
- Обязательный дополнительный канал: оформление оператором по телефону.
- Долгосрочная цель: продавать платформу другим арендодателям по подписке.

## Главный продуктовый принцип

Не разрабатывать одноразовый локальный сайт “под одну компанию”. Нужно с первого коммита строить **multi-tenant SaaS** с изоляцией данных арендаторов.

## Требования к реализации

- Использовать TypeScript для frontend.
- На backend использовать FastAPI + PostgreSQL.
- Соблюдать чистую архитектуру и предсказуемые границы модулей.
- Для multi-tenant данных применять явный tenant scope + серверные проверки + RLS.
- Писать миграции.
- Писать тесты для критических сценариев.
- Не использовать mock-only заглушки как финальную реализацию там, где ожидается реальная бизнес-логика.
- Не внедрять избыточные микросервисы в MVP.

## Что особенно важно

### 1. Телефонные заказы
В системе обязательно должен быть первый класс поддержки заказов, оформляемых оператором по телефону.
Это не “второстепенный комментарий”, а обязательный сценарий.

### 2. Landing page
Главная страница должна быть продающей и конверсионной, а не просто технической заглушкой.
Нужно реализовать hero, CTA, калькулятор стоимости, FAQ, преимущества и мягкие анимации.

### 3. Юридическая осторожность
Сервис не ставит диагноз, не назначает лечение и не заменяет врача.
Любые тексты и UI не должны делать медицинских обещаний.

### 4. Масштабирование на других арендодателей
Любое архитектурное решение проверять вопросом:

> “Сможет ли это работать для десятков независимых арендодателей из разных городов?”

Если нет — решение неверно.

## Формат работы

- Работать небольшими понятными PR.
- Для каждого PR давать summary изменений.
- После каждого значимого шага обновлять документацию, если поведение системы изменилось.
- Не ломать ранее согласованные сценарии.

## Приоритет MVP

1. Маркетинговая landing page
2. Tenant-aware onboarding foundation
3. Auth by SMS (пока с адаптером провайдера)
4. Каталог, доступность и оформление онлайн
5. Оформление заказа оператором по телефону
6. Админка арендатора
7. Уведомления / продления / возвраты
8. Подписка SaaS
